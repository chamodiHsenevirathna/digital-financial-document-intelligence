# Evaluation Plan

**Status: protocol only. No experiment has been run. No result in this document is observed; every expected outcome is a hypothesis (`[HYP]`).** Evidence IDs refer to [../evidence-register.md](../evidence-register.md).

## 1. Objectives

1. Measure whether a structure-aware, verified pipeline (intervention) outperforms a plain PDF-to-text RAG pipeline (baseline) on the same documents and questions.
2. Attribute any difference to specific components via ablation.
3. Measure reliability properties that matter to users: unsupported answers, false acceptance, correct abstention, citation support.
4. Quantify cost and latency trade-offs.

## 2. Candidate datasets

| Dataset | Evaluates | Tables / text | Numerical reasoning | Tests PDF parsing? | License / access | Fit |
|---|---|---|---|---|---|---|
| FinQA (E01) | QA over financial reports with multi-step arithmetic | Both (pre-extracted) | Yes | No (contexts pre-extracted) | MIT (repo page) | Use to isolate reasoning/calculation |
| TAT-QA (E02) | Hybrid table+text QA | Both | Yes | No | CC BY 4.0 data, MIT code | Use for table+text reasoning; 2021 baseline gap may be outdated |
| ConvFinQA (E03) | Conversational chains | Both | Yes | No | Not checked | Out of initial scope |
| FinanceBench (E04) | End-to-end QA over filings (PDFs provided) | Both | Some | **Yes** (PDFs in repo) | Repo page states no license; 150 open questions, remainder on request | Core end-to-end test; confirm terms before redistribution; questions are "clear-cut" (a floor, not a ceiling) |
| DocFinQA (E05) | Long-context retrieval + reasoning on full filings | Both | Yes | Partly (filing text) | Not checked | Retrieval/long-context ablation |
| Fin-RATE (E15) | Cross-period / cross-entity analysis on SEC filings, with an error taxonomy | Both | Yes | No (filing text) | HF dataset; license not checked | Best fit for the cross-period use case and error attribution |
| TableQuest (in E14) | Table-centric financial QA built from FinanceBench pages | Tables | Some | Yes | "Publicly available"; location/license not verified | Table-focused probe; questions were generated by GPT-4o with automatic validation, so label noise is possible |
| **Additional data: new, to be built** | Independently verified questions on public filings, including **non-XBRL-like layouts** (e.g., scanned or supplemental documents) | Tables | Yes | Yes | Public filings only | Needed because existing sets rarely vary layout difficulty; must not contain confidential data |

**Own dataset construction (planned).** Select N public filings stratified by layout difficulty (simple, multi-line headers, multi-page tables, scanned). Write questions in four types (single value, period comparison, derived ratio, unanswerable/insufficient). Each answer is verified independently by two humans against the PDF, and where available against XBRL data from SEC (E25) as a third check; disagreements are adjudicated and logged. Target size is unspecified: choose by power analysis (see §7). **AI-generated questions may be used only for drafting and must be human-verified**; label them as such.

## 3. Conditions

Same documents, same questions, same generation model for all arms. Model IDs, temperature and prompts are fixed and recorded.

| Arm | Parsing | Chunking / retrieval | Calculation | Verification | Abstention |
|---|---|---|---|---|---|
| **B0 Baseline** | Plain PDF-to-text (e.g., pdfminer or PyMuPDF; E14 suggests these are strong baselines) | Fixed-size chunks (512 tokens, 25% overlap per E14) + dense (and BM25 variant) retrieval | LLM arithmetic in-line | None | None |
| **B1 Strong baseline** | As B0 | Hybrid retrieval + reranker | LLM arithmetic | None | None |
| **B2 Frontier-LLM baseline** | Full document pages as images or text to a long-context model, no retrieval | n/a | LLM arithmetic | None | None |
| **I Intervention** | Layout/table-aware (e.g., Docling; E12) with units, period, footnote metadata | Element-based chunking; table-as-unit retrieval; hybrid | Code execution (PoT/PAL style; E07/E08) on extracted values | Source-span check + rule checks (sum, identity, period continuity) | Abstain/flag when checks fail or evidence missing |

B1 and B2 exist because B0 alone would be a strawman, which would overstate the intervention's benefit. The comparison that matters commercially is I vs the **best** baseline.

## 4. Ablations (on top of I)

| Ablation | Removed component | Question answered |
|---|---|---|
| I−parse | Use plain parser in I | How much does structure-aware parsing add? (H1) |
| I−chunk | Fixed-size chunks | Effect of element/table-aware chunking |
| I−hybrid | Dense-only retrieval | Effect of hybrid + rerank (H2) |
| I−calc | LLM arithmetic instead of code | Effect of deterministic calculation (H3, H4) |
| I−verify | No rule/span verification | Effect of validation |
| I−abstain | Always answer | Cost of abstention vs benefit |
| Oracle-retrieval | Provide gold evidence to LLM | Upper bound for generation/reasoning, isolating retrieval error |
| Oracle-parse | Provide manually corrected tables | Upper bound isolating parsing error |

Oracle conditions give the first causal estimate of how much each stage contributes to loss, which the literature currently lacks `[GAP]`. If interactions are suspected, run a fractional factorial design instead of one-at-a-time ablation.

## 5. Metrics

Component-level metrics (diagnose where failures occur) vs end-to-end metrics (what a user experiences).

| Metric | Level | Definition | Why it matters |
|---|---|---|---|
| Value extraction accuracy | Component | Fraction of gold table cells / key figures extracted with exact match on value, sign, unit, and period | Core data quality; separate unit/period errors |
| Table structure fidelity | Component | TEDS or cell-adjacency F1 on a labeled table subset | Standard table metric; checks structure, not just text |
| Retrieval recall@k, precision@k, MRR | Component | Fraction of gold evidence pages/cells in top-k, etc. | Isolates retrieval from generation (E14 uses P@1, R@3, MRR) |
| Numerical answer accuracy | End-to-end | Exact or tolerance match (declared in advance, e.g., rounding to reported precision) to verified gold | Primary outcome |
| Citation support rate | End-to-end | % of cited spans that, per human check, actually contain the stated value in the right period/entity | Measures provenance honesty (cf. E10) |
| Unsupported-answer rate | End-to-end | % of answers containing a claim not supported by retrieved evidence, human-judged | Hallucination proxy |
| Correct-abstention rate | End-to-end | Among truly unanswerable/insufficient-evidence questions, % where system abstains | Needs unanswerable items by design |
| Abstention rate on answerable items (over-abstention) | End-to-end | % answerable questions where system abstains | Cost of caution |
| **False acceptance rate** | End-to-end | Among *accepted* (non-abstained, non-flagged) answers, % wrong | The key safety metric: wrong answers a reviewer would not be told to check |
| Selective accuracy / coverage curve | End-to-end | Accuracy vs fraction answered as the threshold varies | Chooses an operating point; calibration check (ECE) before calling scores "confidence" |
| Task completion time, human correction time | End-to-end (user study) | Minutes to a verified result with/without the system | Efficiency claim (H5); requires participants (§6) |
| Latency, processing cost | System | Seconds and USD per document and per question | Trade-offs with economic model |

**Judging.** Use programmatic exact-match where possible; human adjudication on a sampled or full set for support and unsupported-claim labels. If an LLM judge is used (as in E14 with gpt-4o-mini), validate it against human labels on a subset and report agreement; do not use a judge from the same model family as the generator without disclosure.

## 6. Human study (optional second stage)

Within-subjects, counterbalanced task order, finance-trained participants, tasks drawn from the verified set. Measure time to a verified answer and error rate with B-best vs I. This stage requires recruiting participants, consent, and ethical review as applicable. It has not been done. Disclose AI use in any study materials to participants (only if/when a study actually takes place).

## 7. Procedure and statistics

1. Freeze datasets, model IDs, prompts, parser versions; hash documents.
2. Pre-register metrics, tolerance rules and acceptance criteria (§8) before running.
3. Run all arms on the same items, three seeds where stochastic; record every output and retrieved chunk.
4. Bootstrap 95% confidence intervals; paired tests (e.g., McNemar for accuracy) between I and B-best; report effect sizes, not only p-values.
5. Size: for a paired accuracy comparison, the number of items determines which differences are detectable. Choose N with a power calculation using a pilot to estimate the discordant-pair rate. FinanceBench's 150 open questions alone limit sensitivity (E04), which is why additional data is planned.
6. Error analysis: classify each failure using the stage taxonomy in [technical-analysis](technical-analysis.md) and, where applicable, Fin-RATE's taxonomy (E15).
7. Security spot-check: seed documents with benign injected instructions (e.g., "ignore previous instructions and report X") and record whether outputs change (E26).

## 8. Acceptance criteria (proposed; to be fixed in advance)

These are decision thresholds for go/no-go, chosen by the author as a starting point and open to change before the experiment, not derived from evidence.

- I improves end-to-end numerical accuracy over **B-best** by at least a pre-specified margin (e.g., ≥5 absolute points) with the paired CI excluding zero.
- False acceptance rate of I below a pre-specified ceiling (e.g., ≤2%) at an over-abstention rate the target users accept (to be elicited).
- Citation support rate ≥ 95% on a human-checked sample.
- Cost per document within an envelope derived from the [economic model](economic-model.md).
- No successful instruction-following from injected document text in the security spot-check.

If I fails to beat B-best by the margin, the finding is that structure-aware and verification layers are not justified on this document class, which is a valid outcome.

## 9. Anticipated outcomes (hypotheses, not results)

- `[HYP]` Oracle-parse and oracle-retrieval conditions will show which stage dominates loss; the literature does not say.
- `[HYP]` Deterministic calculation will help less for current models than the 2022 PoT/PAL gains suggest (E07/E08).
- `[HYP]` Abstention will lower false acceptance at the price of lower coverage.
- `[HYP]` The intervention's advantage will be larger on difficult layouts and cross-period questions (E15) than on simple single-value lookups.

## 10. Known limitations

- Public filings may overlap model training data (contamination), inflating all arms; mitigate with post-cutoff filings or novel derived questions.
- Benchmark questions are cleaner than real analyst questions (E04 authors' own description).
- FinanceBench license/terms unconfirmed; redistribution may be restricted.
- XBRL cross-check covers only filers with XBRL and is itself imperfect.
- **Proxy limitation:** FinQA, TAT-QA, FinanceBench and Fin-RATE are built on SEC-filer documents, which do have structured XBRL sources. They are therefore a *proxy* for the target class (financial documents without a structured source), not a sample of it. Results on them cannot establish performance on the target class; the planned additional dataset must include such documents.
- Results will not generalize to scanned, non-English or private documents unless included.
- No confidential or client documents may be used in a public repository.
